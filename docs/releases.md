# Release process

A completed green main CI run triggers the Release workflow. It ignores forks, pull-request runs and failed CI. The preparation job checks out the exact tested commit, reads the version constant and stops if that version is already published or independent review is pending. A draft or partial release can resume automatically only when its tag and draft target match the reviewed commit. An approved release-readiness.json must match a SHA-256 digest of the tracked application, tests, policy examples, distribution notices and build workflows. Review records and TODO.md are excluded to avoid a self-reference. A code or packaging change needs a fresh review digest.

The release build uses the pinned .go-version toolchain. The Go module's minimum remains Go 1.23. Each archive is built and tested on a native runner: Linux amd64 and arm64, macOS Intel and Apple Silicon, and Windows amd64. Each runner records the full test output, builds with CGO disabled, extracts its own archive and smoke-tests that extracted binary. The smoke checks version/help, policy validation, key generation, listener startup, grant issuing and inspection, a scoped refusal, revocation, audit export, and a flight log verify and replay on the smoke database. Unix smoke shutdown uses SIGTERM; Windows smoke cleanup terminates the process. The separate Go tests cover process-kill recovery and context-driven server shutdown.

All native builds must pass before the publication job receives write permission. It checks every archive hash and source commit, reads the fresh Linux/macOS failure-test recordings and Docker/browser artifacts, and writes SHA256SUMS and test-results.json. The measured consumer-race and flight recorder summaries are parsed from the Go test log. CI also shows both summaries as notice annotations. The replay, JSON results and audit export are copied from the actual Docker run. The job then uploads assets and publishes the release using the repository's GITHUB_TOKEN. No personal access token is needed.

The workflow can also be dispatched with ref=main, or with an existing vX.Y.Z tag and rebuild=true. Manual runs execute the reusable CI workflow again, including the Docker demonstration and browser checks, before the native release matrix. A rebuild must use the existing tag's commit; it never moves a tag to new source or changes latest to an older version. Partial uploads can be replaced by a successful automatic resume or rebuild after the actual error is diagnosed. Release jobs keep native test and smoke logs as artifacts even on failure.

Archive names are tokening-linux-amd64.tar.gz, tokening-linux-arm64.tar.gz, tokening-darwin-amd64.tar.gz, tokening-darwin-arm64.tar.gz and tokening-windows-amd64.zip. Each contains the binary, README, policy examples, reference documentation and licence notices. Additional release assets are SHA256SUMS, test-results.json, demo-replay.html, demo-results.json and decisions.jsonl.

After publication, verify the asset list, download an archive through releases/latest/download, check its hash and run the binary. The independent review is a separate agent's source review. It is not a claim of third-party certification or an external security audit.
